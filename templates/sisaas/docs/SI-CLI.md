# The `si` CLI

This project was generated by `si`, and `si` is still the way to change its
shape. The commands below are not conveniences wrapping something you could type
by hand — each one knows things that are easy to get wrong and expensive to get
wrong quietly: which migration number is next, that a module registered in
`app.module.ts` must also be registered in `worker.module.ts`, that a compose
fragment and an `.env` key and an anchor insertion all have to land together.

`si --help` and `si <command> --help` are authoritative. This file is the map.

---

## Every command

| Command | What it does |
|---|---|
| `si new [dir]` | Scaffold a new project |
| `si scaffold <Entity>` | Generate a feature module — schema, migration, repository, service, DTOs, controller |
| `si api <name>` | Add another API service, reusing this project's decisions |
| `si add <tool…>` | Wire an open-source tool in: deps, compose, env, module registration |
| `si list [tools\|features\|all]` | Browse what can be added |
| `si start dev` | Bring up everything and run it |
| `si stop` | Stop the dev stack |
| `si upgrade` | Move onto a newer template without losing your edits |
| `si compliance` | Report this project against a compliance framework |
| `si doctor` | Check the local toolchain |

## `si start dev`

```bash
si start dev                 # containers, migrations, API, worker, web
si start dev --detach        # dependencies only; run the app yourself
si start dev --skip-migrate  # when you are debugging the migration itself
si start dev --scale server=3   # replicas, to exercise the load balancer
si stop                      # stop the containers
si stop --volumes            # and delete the data
```

**Use this rather than `pnpm dev`.** `pnpm dev` starts the API and the web app
but *not* the worker — `worker:dev` is not in turbo's task graph. The worker is
where event delivery and background jobs run, so without it the outbox fills up
and no handler ever fires. The app looks like it works right up until you check
whether anything actually happened.

It also picks host ports that are free. If something already holds 5434 or 9000,
the stack moves around it and `.env` is rewritten to match, so two projects can
run side by side. The ports it chose are printed when it starts.

## `si scaffold <Entity>` — the generator

```bash
si scaffold Product -m catalog
si scaffold Invoice -f "number:string:unique amount:money issuedAt:date"
si scaffold Order --cqrs
si scaffold Setting --no-tenant-scoped --no-events
si scaffold Product --dry-run          # print, write nothing
```

| Flag | Meaning |
|---|---|
| `-m, --module <name>` | Module folder. Defaults to the plural of the entity. |
| `-f, --fields <spec>` | `name:type[:modifier]`, space separated |
| `--cqrs` | Command/query handlers instead of a service |
| `--no-tenant-scoped` | Omit `tenant_id`, its foreign key and the RLS policy |
| `--no-events` | Do not publish domain events to the outbox |
| `--dry-run` | Print what would be written |
| `--force` | Overwrite files that exist |

Field types: `string`, `text`, `int`, `money`, `bool`, `date`, `uuid`, `json`.
Modifiers: `optional`, `unique`, `index`.

**Money is `money`, never `float`.** It becomes `numeric(20,4)` and a decimal
string at every boundary. A float loses cents, and it loses them silently.

**`--no-tenant-scoped` is a decision, not a shortcut.** In a multi-tenant build
the default gives the table a `tenant_id`, a real foreign key, `ENABLE` **and**
`FORCE ROW LEVEL SECURITY`, and the `tenant_isolation` policy. Opting out means
the database stops enforcing isolation for that table and your code becomes the
only thing standing between two customers' data.

What it writes, all of it wired together:

```
database/schema/<module>.ts          the table
drizzle/000N_<module>.sql            the migration, numbered after what exists
modules/<module>/domain/             types
modules/<module>/application/        service (or command/query handlers)
modules/<module>/infrastructure/     repository, taking a transaction
modules/<module>/interface/          controller, DTOs
app.module.ts, worker.module.ts      registration in BOTH
```

The registration in both is the part worth having a generator for. A module
registered only in `app.module.ts` has handlers that never run, and nothing
fails — the events simply stop arriving.

## `si add <tool…>` — open-source services

```bash
si list tools                     # what is available here
si list tools -c search           # by category
si list features                  # prebuilt features, not services
si add meilisearch                # deps, compose, env, module, all at once
si add livekit blnk --dry-run     # see what it would touch
```

One command does: install the dependencies, merge the compose fragment, append
the env keys with dev defaults, render the module, register it at the anchor in
`app.module.ts`, and add any migration with the next free number.

Doing this by hand is where the mistakes are — a compose service with no env
key, a module file with no registration, a migration numbered over one that
already exists.

Re-running is safe: a file that exists is skipped, a compose service already
present is left alone, a migration already applied is not written again.

## `si api <name>` — another service

```bash
si api billing
```

For splitting into separate deployables. It reuses this project's recorded
decisions — layout, data topology, auth — rather than asking again, because two
services that answered "where does the data live" differently is a problem you
find in production.

## `si upgrade` — newer template, your edits kept

```bash
si upgrade --dry-run     # always do this first
si upgrade
```

It replays this project's own composition against the current template and
classifies every file rather than copying it:

| | |
|---|---|
| **added** | new in the template, you do not have it → written |
| **updated** | the template changed it, you never touched it → written |
| **yours** | you changed it, the template did not → left alone |
| **conflict** | both changed it → written as `<file>.si-new`, never over yours |

Commit before running it, so `git diff` shows exactly what moved. Merge each
`.si-new` and delete it; until you do, that file stays a conflict on the next
upgrade rather than being silently resolved in the template's favour.

Tools added with `si add` are not tracked — re-run `si add <id>` for those.

## `si compliance`

```bash
si compliance                 # report, with evidence
si compliance --write         # also write docs/compliance/<id>.md
si compliance --strict        # exit non-zero if anything is missing
si compliance --fix           # install what closes the gaps
```

It reports evidence — the file and line that satisfies a requirement — not
claims. A requirement it cannot prove is reported missing even if you believe it
is handled.

## What `si new` decided here

Recorded in `.si/project.json`, and read back by `si api`, `si scaffold` and
`si upgrade`. Worth reading before you assume how this project is shaped:

- **tenancy** — `multi` (Postgres RLS) or `single` (no tenant column, the guard
  on the route is the whole boundary)
- **events** — `in-process` (a poller calls handlers) or `kafka` (Debezium tails
  the WAL). Publishers and handlers are identical either way.
- **modules** — `service` or `cqrs`. `si scaffold` follows it without a flag.
- **auth** — `builtin`, `keycloak`, `zitadel` or `none`
- **layout** — `mono`, `identity` or `service`

Changing `events` after the fact is a one-line edit in `app.module.ts` and
`worker.module.ts` plus the compose services; `si upgrade` will not do it for
you.
