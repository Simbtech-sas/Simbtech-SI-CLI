# The `si` CLI

This project was generated by `si`, and `si` is still the way to change its
shape. `si --help` and `si <command> --help` are authoritative; this file is the
map.

Some commands only apply to the server flavours (SiSAAS / SiAPP) — `si scaffold`
needs an `apps/server`, and `si start dev` needs `infra/docker-compose.yml`.
Those are noted below.

---

## What applies here

| Command | What it does |
|---|---|
| `si list [tools\|features\|all]` | Browse what can be added. Filtered to this flavour. |
| `si add <tool…>` | Wire a tool in: deps, config, registration — together |
| `si upgrade` | Move onto a newer template without losing your edits |
| `si doctor` | Check the local toolchain |
| `si new [dir]` | Scaffold another project |

---

## `si add <tool…>`

```bash
si list tools                  # what is available for this flavour
si list tools -c search        # by category
si add <id> --dry-run          # see what it would touch
si add <id>
```

One command installs the dependency, merges any config, appends env keys with
dev defaults, and registers what needs registering. Doing it by hand is where
the mistakes are — a service with no env key, a module file nothing imports.

Re-running is safe: files that exist are skipped.

`si list` only offers what makes sense here. A tool that is not listed is not
an oversight — it does not fit this flavour.

---

## `si upgrade`

```bash
si upgrade --dry-run     # always this first
si upgrade
```

It replays this project's own composition against the current template and
classifies every file rather than copying it:

| | |
|---|---|
| **added** | new in the template, you do not have it → written |
| **updated** | the template changed it, you never touched it → written |
| **yours** | you changed it, the template did not → left alone |
| **conflict** | both changed it → written as `<file>.si-new`, never over yours |

Commit first, so `git diff` shows exactly what moved. Merge each `.si-new` and
delete it; until you do, that file stays a conflict on the next upgrade rather
than being quietly resolved in the template's favour.

Tools added with `si add` are not tracked — re-run `si add <id>` for those.

## Server flavours only

These need an `apps/server` and a compose file, so they apply in a SiSAAS or
SiAPP project rather than this one:

- `si scaffold <Entity>` — a feature module wired end to end, registered in both
  `app.module.ts` and `worker.module.ts`
- `si start dev` — containers, migrations, API, worker and web, on free ports
- `si api <name>` — another API service, reusing the project's decisions
- `si compliance` — report against a compliance framework, with evidence

If a feature belongs on the server, scaffold it there. Most do.
